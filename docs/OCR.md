# Receipt OCR (Phase 9)

OCR is asynchronous. A receipt is created only after its private original upload succeeds. A DynamoDB `INSERT` stream event starts Textract `StartExpenseAnalysis` with a deterministic, owner-and-receipt-scoped client request token and the receipt ID as the job tag. The API request does not wait for OCR. Textract publishes completion to the stack's `AmazonTextract-Cubby` SNS topic, which invokes the completion Lambda. This is the completion channel required by Textract; the flow adds no SQS queue or polling worker.

The starter reads the receipt from its owner partition and accepts only the exact `{owner}/originals/{uuid}` key generated for immutable uploads. The completion handler checks the SNS bucket, key, API operation, job ID and owner against that stored record before reading results. `GetExpenseAnalysis` follows every `NextToken`. Extracted values are stored separately from user-entered metadata. Missing, low-confidence, duplicate, multi-document or partial results become `REVIEW_NEEDED`; complete, high-confidence results become `READY`. Invalid originals and Textract terminal failures become `OCR_FAILED`.

Both DynamoDB stream and SNS delivery can repeat. Starting the same receipt uses the same Textract idempotency token, and every persistence transition checks the current status, job ID and object key atomically. Duplicate or late completions cannot replace an already final result. A completion arriving before the start job ID is committed raises an error so the event can retry. Transient Textract and DynamoDB errors also propagate for platform retries without marking a receipt as terminal. Stream processing is limited to one receipt per batch, ten retries and six hours of record age; after retries are exhausted, the current status remains available for diagnosis rather than silently claiming OCR succeeded. Textract's internally stored asynchronous results expire after seven days. A later operational recovery path would require a separately scoped milestone.

The starter can read only original objects, update only the receipt table and call `StartExpenseAnalysis`; it may pass only the stack's Textract notification role. The completer can update the receipt table and call only `GetExpenseAnalysis`. The Textract role can publish only to the stack's SNS topic. Textract's start/get operations and DynamoDB `ListStreams` do not support a narrower IAM resource ARN; all other grants use the table, stream, topic, role, log group or original-object ARN. Local tests mock AWS clients, and CDK synthesis uses `--no-lookups`; no cloud services are invoked by validation.
